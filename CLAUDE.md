## Обязательное по инструкции участника

Это не рекомендации, а условия зачёта — из отдельных инструкций организатора, которые дополняют Положение.

**Использование AI-агента обязательно.** Формулировка организатора: «Главное — использовать AI-агента и разместить итоговый код в GitHub-репозитории команды». То есть работа через Claude Code этому требованию соответствует, но факт использования AI-агента должен быть виден и отражён в README.

**Личный вклад каждого участника обязателен.** Участие не засчитывается тому, кто не внёс личный вклад в проект. Практически: **у каждого из троих должны быть собственные коммиты** в репозитории, а не «за всех коммитит капитан». Это проверяемо и по истории, и по метаданным.

**Секреты в репозиторий не попадают.** Прямой запрет на размещение паролей, API-ключей и токенов в исходном коде, репозиториях, презентациях и чатах. Перед публикацией проект проверяется на их наличие. У нас для этого есть `.gitignore` и `.env.example`; ключи живут только в локальном `.env`.

## Сеть и безопасность на площадке

- Сеть на площадке **проводная Ethernet**. Нужен переходник USB/USB-C → RJ-45, с заранее установленным драйвером и проверенный на практике
- IP и DNS — **автоматическое получение (DHCP)**. Ручные настройки заранее отключить
- Подключаться только к официальной сети хакатона. **Свои точки доступа, раздача с телефона, личные роутеры и модемы запрещены**
- Сеть хакатона — общая недоверенная среда. Доступ к устройствам, аккаунтам и проектам других команд запрещён
- Не использовать реальные продуктивные данные без разрешения
- После мероприятия удалить временные ключи, токены и локальные копии выданных данных

Отдельная оговорка про AI-сервисы: инструкция по кибербезопасности запрещает передавать им конфиденциальную информацию и чужой исходный код без разрешения организаторов. При этом инструкция для участников прямо предписывает разрабатывать проект через AI-агента. Противоречия нет: работа с **нашим собственным** проектным кодом разрешена явно, запрет касается конфиденциальных и чужих данных. Результаты, выданные AI, участник обязан сам проверить на корректность и безопасность.

## Окружение и запуск

Два пути запуска, **один источник зависимостей**. Манифест один (`pyproject.toml` / `requirements.txt`), оба пути читают его. Расхождение путей = один из них молча сломается.

- **Основной путь** — `docker compose up`, одна команда
- **Запасной путь** — запуск без Docker, описан в README. Страховка не от нашей ошибки, а от чужой: у эксперта может не быть Docker, не запуститься демон, не совпасть архитектура

Порядок работы с образом — «поднять в начале и держать зелёным»:

| Когда | Что |
| --- | --- |
| Час 0, ~10 мин | Минимальный образ поднимает пустой скелет. Доказываем, что конвейер работает |
| Непрерывно | Любая новая зависимость идёт в манифест **сразу**. `pip install` локально без записи в манифест = проект не заработает у эксперта |
| Час 4 | Жёсткая проверка: чистый клон, сборка без кеша, прогон основного сценария |

Подводные камни, которые надо держать в голове:

- **Архитектура.** Разработка идёт на Apple Silicon (arm64), эксперт скорее всего на x86_64. Но образ он собирает у себя из нашего Dockerfile, а базовый образ мультиархитектурный — значит само по себе это не ломается. Платформу принудительно не фиксировать (это загонит нас в медленную эмуляцию). Реальный риск — зависимость без колеса под нужную архитектуру; всплывёт на проверке чистой сборки
- **Вес образа.** Работаем через API, тяжёлые ML-зависимости не тащим без необходимости — иначе сборка станет медленной
- **Пинить версии** базового образа и Python
- **Секреты только через переменные окружения**, никогда в образ

По п. 6.12: если конкурсная версия не запускается, эксперты могут запросить пояснения по окружению, **но пояснения не должны менять код, зависимости, данные или алгоритмы**. То есть починить нельзя. Путь запуска обязан быть проверен до закрытия репо.

## Рабочие договорённости

- **Язык документации проекта — русский.** README, комментарии для жюри, описание — на русском. Код и идентификаторы — на английском, как обычно.
- **Ветку заводит тот, кто делает задачу** — под тикет или под фазу, как удобнее. Закончил, слил в main, конфликт решил сам. Короткую задачу можно сделать и прямо в main. Главное — готовое уезжает в main сразу по готовности, а не копится к стыку фаз. И каждый трогает свои файлы: заметил проблему в чужом лейне — скажи владельцу, а не правь сам.
- Сообщения коммитов — осмысленные, с номером тикета: `[HACKAI-N] что сделано`. Не «fix», «update», «wip».
- **Перед каждой новой задачей — `git pull`, первым действием.** До чтения тикета и до чтения файлов. Пока делал предыдущую задачу, двое других что-то слили в main: новые функции, изменённые сигнатуры, обновлённый `BRIEF.md`. Начать без `pull` — работать на устаревшем слепке и узнать об этом при слиянии.
- **Закончил тикет — оставь след для остальных.** Комментарий в тикете Linear: что сделано, **что теперь можно звать** из других потоков, отклонения от плана, файлы, команда проверки. Без комментария тикет не закрыт. Форма в скилле `case-start`, раздел «Следы работы».
- **`PROGRESS.md` ведёт только Claude капитана.** Это единственный файл, интересный всем сразу; если в него пишут трое, он превращается в постоянный конфликт. Остальные читают, но не правят.
- **Разошёлся контракт — сказать немедленно.** Если реализация отошла от того, что записано в `BRIEF.md`, это пишется первой строкой в комментарии и проговаривается вслух. Молча разошедшийся контракт всплывает на интеграции, когда переделывать уже некогда.
- Не добавлять зависимости и абстракции, которые не нужны прямо сейчас. За 5 часов лишняя сложность дороже, чем кажется.
- Перед тем как сказать «готово» — проверить, что проект реально запускается по инструкции из README.
