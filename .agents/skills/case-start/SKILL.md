# Работа над кейсом HackAlem AI в Codex

Общие правила — `AGENTS.md` в корне проекта. Состояние — `PROGRESS.md`, решение и контракт — `BRIEF.md`, задания и комментарии — Linear. Пути к файлам проекта ниже указаны от корня репозитория.

## Выбери режим по запросу

- **Продолжение работы / конкретный HAC-тикет:** фаза 0 уже выполнена. Не пересоздавай документы, модели, стек, лейблы и тикеты. Выполни текущую задачу по разделу «Цикл тикета».
- **Координация команды капитаном:** сверяй потоки, блокировки, отсечки и готовность сдачи. Только агент капитана обновляет `PROGRESS.md`.
- **Первый старт действительно нового кейса:** получи исходное ТЗ, специальные критерии, время закрытия и дополнительные инструкции; примени раздел «Первоначальная нарезка».
- **Соревнование закончено:** конкурсный код заморожен; работай над материалами Demo Day по запросу.

Расписание относится к 23.09.2026, время Астаны. Не определяй текущую фазу только по старой заметке: сверяй время, свежие коммиты, состояние и поручение пользователя.

## Текущий кейс

AI Sana Challenge Hub. Путь: черновик → минимум три уместных вопроса → редактируемая карточка → рейтинг → публикация → отклик → ручное решение бизнеса.

Три потока уже определены: Дарья — `ядро`, Анель — `поверхность`, Азамат — `обвязка`. Точные файлы, сигнатуры и маршруты брать из `BRIEF.md`, не из примера тикета.

Обязательные свойства сохранять при сокращении объёма: подтверждение человеком, прозрачный рейтинг с недостающими сведениями и пересчётом, общий каталог независимо от низкого рейтинга, неограниченные отклики, ручной выбор одной/нескольких/ни одной команды. ИИ не выдумывает факты, не использует персональные и чувствительные признаки участников и не назначает исполнителей.

OpenAI — основной провайдер; NVIDIA — резерв по брифу. Вызовы SDK только через `app/llm.py`, настройки через `app/config.py`. Не добавляй другие AI-сервисы и модели ради самого подключения. Имена и доступность моделей проверяй при реальной интеграции, а не бери из старых примеров. Локальный AI fallback разрешён кейсом при недоступности API: режим раскрыт, промпт и вход/выход показаны, некорректный ответ обработан. Заглушки остальных модулей нужны для ранней интеграции, но не заменяют обязательную рабочую логику при сдаче.

## Цикл тикета

1. Перед разработкой проверь `git status --short --branch`; при чистом дереве синхронизируй текущую upstream-ветку через `git pull --ff-only`. При незакоммиченных изменениях или расхождении не делай автоматический stash/reset/force push. Правила синхронизации и разрешений — в `AGENTS.md`.
2. Прочитай свежие `AGENTS.md`, `PROGRESS.md`, `BRIEF.md`, весь тикет и комментарии его зависимостей. Проверь, что обещанные интерфейсы действительно появились в коде.
3. Работай в своём потоке и списке файлов тикета. Одна активная задача на участника. Статус In Progress ставь, только если работа с Linear входит в поручение.
4. Реализуй минимальный результат по контракту. Ветку исполнитель выбирает сам (`HAC-N`); короткая задача допустима прямо в main. Не переключай ветки поверх чужой незавершённой работы.
5. Если нужен чужой файл или изменение контракта, обозначь точные изменения владельцу через пользователя/разрешённый канал. В отчёте изменение контракта — первая строка. Не меняй сигнатуры молча.
6. Выполни мини-тест и необходимые проверки. Для кода перед интеграцией — `make check`; если Docker недоступен, сообщи ограничение и результат локального `python -m pytest -q`. Локальные тесты не выдавай за проверку Docker.
7. Добавляй в коммит только свои файлы. Сообщение: `[HAC-N] что сделано`, номер реального тикета. Проверь diff и отсутствие секретов без вывода значений ключей. Не меняй автора коммитов за других участников.
8. При порученной сдаче тикета интегрируй и отправь готовое в main сразу. После конфликтов проверь затронутое поведение. Не объявляй локальный коммит опубликованным.
9. После проверок и push оставь отчёт и затем переведи тикет в Done. Шаблоны — [references/tickets.md](references/tickets.md). Если внешние действия недоступны или не поручены, подготовь отчёт пользователю и явно перечисли несделанные действия.

Порядок завершения: **код → проверка → коммит → main/push → отчёт → Done**.

Если застрял более чем на 15 минут, сообщи причину, что пробовал и что нужно. Не жди стыка фаз. Агент не обещает фонового мониторинга после окончания сессии.

На тикете: исполнитель, одна фаза (`фаза-0`…`фаза-4`), один поток, `мастхэв` или `потом`. Дополнительные свойства: `демо-путь`, `блокер`, `быстрая` (до 15 минут), `свободная-очередь`, `черновик`. Blocks/blocked by отражать в связях и описании.

Статусы: Backlog — будущий неуточнённый тикет; Todo — готов к работе; In Progress — взят; Done — проверен и в main с отчётом; Canceled + `потом` — отложен с причиной.

Тикет самодостаточен: цель, существующий код, точный контракт, границы файлов и проверяемый результат. Оценка обычно 30–60 минут; больше часа — раздели. Не создавай дубликаты уже существующей работы.

Используй доступное подключение Linear. `.mcp.json` и команда `/mcp` из Claude не являются инструкцией для Codex. Если инструменты недоступны, не выдумывай результаты: подготовь текст тикетов/отчётов локально или в ответе, продолжай независимую работу.

## Фазы и отсечки

| Фаза | Время | Результат |
| --- | --- | --- |
| 0 | 13:30–13:50 | Бриф, контракт, распределение файлов, скелет, первый коммит |
| 1 | 13:50–15:00 | Сквозной путь с временными заглушками |
| 2 | 15:00–16:30 | Настоящая логика и обязательные требования |
| 3 | 16:30–17:30 | Ошибки, надёжность, полировка демо |
| 4 | 17:30–18:30 | Заморозка функций, README, чистая сборка, подача |

Наши отсечки: **15:30** — черновая подача; **17:30** — прекращение расширения функций; **18:00** — чистая сборка; **18:15** — финальные коммиты. Окно **13:30–18:30**, значения уже учитывают перенос на 30 минут; источник — `BRIEF.md`, раздел «Отсечки». Фактический дедлайн задаёт организатор. Подача — отдельное действие на платформе, коммит её не заменяет.

Сверка на стыке фаз — примерно пять минут: состояние main и проверок → оставшиеся обязательные пункты → сокращение объёма → уточнение следующей фазы в Linear → обновление PROGRESS агентом капитана. Будущие черновики переводятся в Todo только после уточнения. Решение о сокращении принимает капитан; если он недоступен — ответственный за сдачу сообщает принятое решение капитану. Невыполненный обязательный пункт фиксируй как ограничение, не переименовывай его в необязательный.

При сокращении сначала убирай необязательное вне демо-пути. Можно упростить оформление, но нельзя потерять обязательную информацию и работающие переходы.

## Против простоя

Приоритет: блокер в своей зоне → свободная очередь → незаблокированный тикет своего потока следующей фазы → отделимая помощь в новых или согласованных файлах. Не уходи более чем на одну фазу вперёд и не нарушай владельцев файлов ради свободной очереди.

Свободная очередь: демо-примеры, граничные проверки, разделы README, актуализация env-примера, схема архитектуры, скриншоты и запись, текст подачи. Деплой — только если основное готово и он поручен.

Агент капитана во время активной координации раз в 20–30 минут и перед стыком читает свежие отчёты, замечает блокировки, уточняет очередь и сводит честное состояние в PROGRESS. Остальные этот файл только читают.

## Первоначальная нарезка — только для нового кейса

1. Получи дословное задание и критерии; не задерживай независимую подготовку из-за недостающей несущественной детали.
2. За первые десять минут подготовь краткий бриф и каркас из `prep/templates/`, не перезаписывая существующий проект. Бриф: проблема, обязательные цитаты, критерии, проверяемый результат, слои, потоки, контракт, стек, провайдеры, «потом», время.
3. Выпиши реальные слои и объём, затем раздели на три потока с минимальным пересечением файлов, сопоставимой нагрузкой и минимумом блокировок. Сдача всегда имеет владельца, обычно капитана. Сильные стороны людей — подсказка, а не жёсткая специализация.
4. Запиши точные сигнатуры и форматы на стыках в бриф. Согласуй новые продуктовые решения и распределение с капитаном, если они ещё не согласованы; не запрашивай повторное одобрение существующего плана.
5. Создай детальные задачи фаз 0–1, последующие — черновиками. Резервируй последний час на сдачу. Если обязательное не помещается, предложи конкретное сокращение капитану.
6. Проверь ранний сквозной запуск и сделай осмысленный первый коммит при порученной разработке. Не создавай пустые коммиты ради отчётности.

## Перед сдачей

- Есть пять черновиков, пять карточек, пять профилей команд, пять откликов; данные синтетические при отсутствии выданного набора.
- Работает полный демонстрационный путь на подготовленном примере за пять минут, включая рост рейтинга.
- `make verify` проходит; запасной запуск по README проверен. Новые зависимости записаны в единственный манифест `requirements.txt`.
- README содержит архитектуру, формулу рейтинга, правила каталога, тестовые сценарии, запуск, данные, AI-режим, известные ограничения, использование AI-агента и ранее созданные материалы/внешние зависимости.
- Секретов нет в исходниках, diff, истории подготовленных коммитов и материалах; не печатай ключи при проверке. Один поиск по префиксу не является доказательством отсутствия всех секретов.
- Реальный вклад всех троих виден в истории (`git shortlog -sn HEAD` — вспомогательная проверка, не основание подделывать авторство).
- Решение подано и обновлено до финальной версии, если подача поручена и выполнена. Статус подтверждён фактически.
- Скриншоты/запись подготовлены как страховка, но не подменяют работающий MVP. После закрытия не изменять конкурсную версию; не утверждать без основания, что показать или записать зафиксированную версию позже запрещено.
