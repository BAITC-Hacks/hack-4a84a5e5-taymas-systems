# AI Sana Challenge Hub — от бизнес-задачи к решению

Трек 07 «Образование». Кейс: «AI Sana Challenge Hub: от бизнес-задачи к решению» (владелец задачи — МНВО, AI Sana). Команда TayMas Systems, хакатон HackAlem AI, 23.09.2026.

> README дописывается по ходу дня. Разделы, помеченные «в работе», описывают то, что ещё не в репозитории — на момент закрытия репозитория таких пометок не останется.

## Краткое описание

Бизнес описывает задачу для студентов слишком коротко, и командам непонятно, за что браться. Приложение помогает представителю бизнеса превратить черновик в полноценную карточку задачи: ИИ задаёт уточняющие вопросы, система считает прозрачный рейтинг готовности от 0 до 100 по шкале кейса и публикует карточку в открытом каталоге. Студенческие команды сами выбирают задачи и откликаются, а бизнес вручную решает, с кем работать. Чем полнее описана задача, тем выше её рейтинг и позиция в каталоге — это и есть геймификация для бизнеса.

## Что реализовано

*(в работе — заполняется по мере закрытия тикетов; описывается только то, что есть в коде)*

- **Рейтинг готовности задачи**: 0–100 по семи показателям кейса, расшифровка каждого начисления, список недостающих сведений, четыре уровня готовности. Детерминированный, без языковой модели
- **Обёртка над LLM**: один вызов для OpenAI и NVIDIA, JSON-ответ с проверкой по схеме, повтор при невалидном ответе, работа без ключа
- **Уточняющие вопросы и сборка карточки**: модель определяет пробелы по показателям рейтинга и задаёт не менее трёх вопросов, а затем собирает из черновика и ответов карточку, не добавляя фактов, которых не сообщил пользователь. Без ключа API обе функции работают на локальной заглушке
- **Каталог задач**: все опубликованные задачи, сортировка по подтверждённому рейтингу, фильтры по отрасли и уровню готовности, выделение приоритетных задач и пометка «требует уточнения» у черновиков
- **Страница задачи**: все поля карточки, расшифровка рейтинга по показателям, отклики команд без ограничения числа и ручное решение бизнеса по каждому отклику
- **Рекомендации командам**: в каталоге команда выбирает себя и видит до трёх подходящих задач с объяснением совпадения по интересам, технологиям и отрасли. Только задачи с баллом от 40 — уровень «Рабочая», с которого кейс разрешает рекомендовать; каталог ниже остаётся полным. Детерминированно, без модели
- **Испытание задачи**: до публикации карточку «пробует взять» виртуальная студенческая команда из сида — план первой недели только по карточке, «Стоп» на первом блокере, цена каждого блокера в баллах и следующий шаг. Вердикт детерминирован, тексты пишет модель, без ключа — заглушка. Баллов не начисляет
- **Оформление**: три переключаемых цветотипа, редактор с кольцом рейтинга и «наклейками» по семи показателям, которые открываются по мере заполнения
- Хранилище с синтетическими данными кейса (5 черновиков, 5 карточек, 5 команд, 5 откликов), `/health` для проверки состояния
- Запуск одной командой через Docker и запасной путь без Docker

## Как работает решение

Сквозной сценарий кейса, восемь шагов; в MVP реализованы шаги 1–7 (шаг 8 «баллы команде за прогресс» кейсом не требуется — «полный проектный трекер не нужен»):

1. **Черновик.** Представитель бизнеса вводит короткое описание потребности и выбирает отрасль.
2. **Уточнение.** Система определяет, каких сведений не хватает для рейтинга, и задаёт не менее трёх уточняющих вопросов, привязанных к тексту черновика.
3. **Карточка.** Из черновика и ответов собирается редактируемая карточка с десятью полями: название, контекст, потребность, пользователи, данные, ограничения, ожидаемый результат, критерии успеха, контакт, формат взаимодействия.
4. **Рейтинг.** По семи показателям кейса начисляются баллы; панель показывает, сколько начислено за каждый и что дописать. После каждого сохранения балл пересчитывается.
5. **Каталог.** После ручного подтверждения карточка публикуется. Каталог сортирует задачи по рейтингу и фильтрует по отрасли и уровню готовности; низкий рейтинг задачу не скрывает, а помечает.
6. **Выбор студентов.** Любая команда открывает задачу и отправляет отклик: идея, план, срок, ссылка на прототип. Число откликов не ограничено.
7. **Выбор бизнеса.** Бизнес видит список откликов и вручную выбирает или отклоняет каждый. Автоматического назначения нет.

Сверх кейса между шагами 4 и 5 бизнес может запустить **испытание задачи**: виртуальная команда планирует первую неделю только по карточке и называет блокеры с ценой в баллах (раздел «AI-функции»). А команда на шаге 6 может выбрать себя в каталоге и увидеть рекомендованные задачи с объяснением.

## Формула рейтинга задачи

Рейтинг считается детерминированно, без языковой модели: правила видны в `app/rating.py` и покрыты
тестами `tests/test_rating.py`. Веса — из раздела 4 кейса.

У каждого показателя три уровня начисления: **0**, **половина веса** или **полный вес**. Половина —
поле заполнено осмысленным текстом. Полный вес — в тексте есть конкретика, которую требует кейс.
Поле считается заполненным, если после обрезки пробелов его длина не меньше порога и текст не
является отговоркой («нет», «не знаю», «уточняется», «n/a» и подобными): иначе любая непустая
строка засчитывалась бы как ответ.

| Показатель | Вес | Половина веса | Полный вес |
| --- | --- | --- | --- |
| Контекст и потребность | 20 | описан контекст (10) | описана и потребность (ещё 10) |
| Данные и материалы | 20 | данные описаны | указан формат, объём или пример: CSV, Excel, PDF, API, число записей |
| Ожидаемый результат | 15 | результат описан | назван конкретный артефакт: прототип, сервис, отчёт, дашборд, бот, интерфейс |
| Критерии успеха | 15 | критерии описаны | есть измеримый признак: число, процент, «не менее», «снизить», «время», «точность» |
| Ограничения | 10 | ограничения описаны | назван срок, технология, доступ или бюджет |
| Пользователи | 10 | пользователи описаны | названы роли или количество |
| Связь с бизнесом | 10 | есть контакт: почта, телефон или имя (5) | описан формат консультаций и обратной связи (ещё 5) |

**Уровни готовности:** 0–39 черновик (видна в каталоге, помечена «требует уточнения») · 40–69 рабочая ·
70–89 готовая (выше в каталоге) · 90–100 приоритетная (выделяется в каталоге).

**Подтверждение.** Кейс: «Баллы начисляются только за заполненные и подтверждённые поля». Поэтому
балл, записанный у задачи и влияющий на её позицию в каталоге, обновляется только при подтверждении
человеком. После обычного редактирования показывается предварительный балл, а подтверждённый остаётся
прежним, пока представитель бизнеса не нажмёт подтверждение. Так же обрабатываются правки уже
опубликованной задачи.

**Примеры начисления.** «Есть какие-то данные по продажам» — 10 из 20, потому что нет формата и объёма.
«Выгрузка 50 000 заявок за 18 месяцев в CSV» — 20 из 20. «Сделать удобно и быстро» — 8 из 15, нет
измеримого признака. «Доля ручных проверок падает с 40% до 20%» — 15 из 15.

## Правила каталога

- В каталоге видны все опубликованные задачи, всем командам, без регистрации.
- Порядок — по убыванию рейтинга; при равном балле выше более свежая публикация.
- Фильтры: отрасль и уровень готовности. Фильтры сужают показ, но не скрывают задачи навсегда.
- Низкий рейтинг не запрещает отклик и не прячет задачу — он показывает командам, насколько реально начать работу без дополнительных уточнений.
- Рейтинг пересчитывается после каждого подтверждённого редактирования, и позиция в каталоге меняется вместе с ним.

## AI-функции

Кейс требует минимум одну содержательную AI-функцию и просит показать промпт, формат входа,
формат выхода и обработку некорректного ответа. Ниже всё это по каждой из трёх функций.

### Генерация уточняющих вопросов

**Что делает.** По черновику бизнеса система считает рейтинг, находит показатели с недобором
и просит модель задать вопросы именно по ним. Вопрос закрывает ровно одно поле карточки,
поэтому ответ сразу попадает в нужное место.

**Вход модели** — черновик, отрасль и список показателей с недобором, отсортированный по величине
пробела (`app/prompts.py`, `build_questions_user_prompt`):

```
Отрасль: Образование
Черновик задачи от бизнеса:
Хотим чат-бота для студентов, чтобы отвечал на вопросы.

Показатели рейтинга с недобором (более важные — выше):
- Данные и материалы: начислено 0 из 20 баллов
- Критерии успеха: начислено 0 из 15 баллов
- Ожидаемый результат: начислено 0 из 15 баллов
```

**Системный промпт** (`app/prompts.py`, константа `QUESTIONS_SYSTEM`, приводится дословно):

```
Ты помогаешь представителю бизнеса дополнить черновик задачи для студенческой команды.
Правила:
- Задай от 3 до 6 уточняющих вопросов, каждый закрывает ровно одно поле карточки.
  Поле — строго одно из: title, context, need, users, data, constraints,
  expected_result, success_criteria, contact, interaction_format.
- Вопрос должен опираться на конкретные детали черновика, а не быть общим шаблоном.
- Никогда не предлагай готовых вариантов ответа и не добавляй фактов, которых нет
  в черновике или в списке пробелов ниже.
- Не спрашивай про персональные данные конкретных людей (студентов, сотрудников).
- Пиши только на русском языке.
```

**Выход модели** — JSON по схеме `QuestionsResponse`, проверяется через pydantic:

```json
{"questions": [{"field": "data", "question": "...", "why": "Данные и материалы — 20 баллов"}]}
```

**Обработка некорректного ответа.** Три рубежа, каждый ниже предыдущего:

1. Ответ не по схеме или не JSON — обёртка `app/llm.py` делает один повторный запрос с текстом ошибки
   и просьбой прислать исправленный JSON.
2. Ответ формально валиден, но бессмысленен — проверяется количество вопросов, принадлежность поля
   списку полей карточки, непустые тексты и отсутствие дублей по полю. Не прошло — результат отбрасывается.
3. Модель недоступна, ключа нет или проверки не пройдены — включается локальная заглушка: вопросы
   собираются по тем же показателям с недобором из заранее заготовленных формулировок.

Во всех трёх случаях пользователь получает рабочие вопросы, а приложение не падает. Текущий режим
виден в подвале страницы и в ответе `/health`: `openai`, `nvidia` или `stub`.

### Сборка карточки из ответов

**Что делает.** Черновик и ответы на уточняющие вопросы раскладываются по десяти полям карточки.
Это вторая содержательная AI-функция: кейс требует минимум одну, у нас обе рекомендованные —
и анализ полноты с вопросами, и преобразование ответов в карточку.

**Вход модели** — черновик, отрасль и пары «вопрос — ответ» (`app/prompts.py`, `build_card_user_prompt`):

```
Отрасль: Образование
Черновик задачи от бизнеса:
Хотим чат-бота для студентов, чтобы отвечал на вопросы.

Ответы на уточняющие вопросы:
- [data] Какие данные, примеры или источники вы можете передать команде?
  Есть FAQ на 120 вопросов в Google Docs, расписание на семестр в Excel,
  лог обращений за год — около 3 000 сообщений.
```

**Системный промпт** (`app/prompts.py`, константа `CARD_SYSTEM`, приводится дословно):

```
Ты собираешь карточку задачи для студенческой команды из черновика бизнеса и его ответов на уточняющие вопросы.
Правила:
- Используй только сведения, явно указанные в черновике и в ответах. Ничего не додумывай.
- Если для поля во входе нет информации, оставь его пустой строкой "".
- Не придумывай сроки, объёмы, контакты, названия и другие факты, которых не назвал пользователь.
- Поле title — не длиннее 80 символов, отражает суть задачи.
- Пиши только на русском языке.
- Ответ строго JSON с ключами: title, context, need, users, data, constraints, expected_result, success_criteria, contact, interaction_format.
```

**Выход модели** — JSON с десятью полями карточки, проверяется через pydantic по схеме `CardFields`.

**Защита от выдуманных фактов.** Главное требование кейса к этой функции. После ответа модели
каждое непустое поле проверяется на «укоренённость»: длинные слова из него ищутся по корням
в исходном тексте — черновике и ответах. Поле, в котором слишком много слов не из источника,
**отбрасывается и заменяется значением заглушки**, то есть тем, что человек написал сам.
Поэтому модель физически не может дописать в карточку цифру, срок или название, которых не было.

Проверено на реальном вызове: из черновика про чат-бота и одного ответа про данные модель
заполнила три поля, **остальные семь оставила пустыми** — ровно так и должно быть.

**Обработка некорректного ответа** — те же три рубежа, что и у вопросов: повтор запроса при ответе
не по схеме, отбраковка при непройденных проверках, локальная заглушка как последний рубеж.
Заглушка раскладывает ответы по полям напрямую, без переформулировки.

### Испытание задачи: виртуальная команда

**Что делает.** Сверх требований кейса. До публикации бизнес может «дать» карточку одной из
студенческих команд сида: команда, зная только текст карточки, планирует первую неделю и
останавливается там, где сведений нет. Результат: вердикт «выдержала / не выдержала», план с шагом
«Стоп», блокеры с ценой в баллах и следующий шаг вида «заполните „Данные и материалы“ (+20) — балл
станет 55, уровень „Рабочая“». Это ответ на вопрос «можно ли по этой карточке начать в понедельник»,
а не оценка: **баллы за испытание не начисляются**, рейтинг по-прежнему только за подтверждённые поля.

**Что решает правило, а что модель.** Вердикт и состав блокеров — детерминированное правило поверх
рейтинга (`app/trial.py`, `BLOCKING_KEYS`): старт блокируют недоборы по показателям «Контекст и
потребность», «Данные и материалы», «Ожидаемый результат», «Пользователи»; недоборы по «Критериям
успеха», «Ограничениям» и «Связи с бизнесом» — риски, начать можно. Поэтому карточка на 60 баллов без
данных испытание не выдержит, а на 55 с данными — выдержит: испытание и рейтинг измеряют разное.
Модель пишет только тексты — план первой недели и формулировки причин.

**Вход модели** (`app/trial.py`, `build_trial_user_prompt`) — профиль команды, карточка целиком и списки
блокеров и рисков с тем, чего не хватает. Реальный пример для слабой карточки и команды DataBee из сида:

```
Команда DataBee. Интересы: образование, рекомендательные системы, чат-боты. Навыки: анализ данных, бэкенд, интерфейсы. Технологии: Python, FastAPI, PostgreSQL, React.

Карточка задачи (отрасль: Образование):
- Название: Подбор наставников для первокурсников
- Контекст: что происходит сейчас: В первый семестр около трети первокурсников не находят наставника, кураторы распределяют вручную по спискам групп.
- Потребность: что нужно изменить: Нужен сервис, который предлагает куратору трёх подходящих наставников на каждого первокурсника.
- Пользователи: для кого решение: Кураторы факультетов и первокурсники.
- Данные и материалы: — не заполнено
- Ограничения: сроки, технологии, доступы: — не заполнено
- Ожидаемый результат: — не заполнено
- Критерии успеха: — не заполнено
- Контакт: — не заполнено
- Формат взаимодействия и обратной связи: — не заполнено

Блокеры — сведения, без которых начать нельзя:
- key=data — Данные и материалы: Нет данных, примеров или источников: команде не с чем начать разбор в первую неделю. Что добавить: Опишите доступные данные: формат, объём и пример.
- key=expected_result — Ожидаемый результат: Не описан результат работы: команда не поймёт, что именно сдавать. Что добавить: Опишите ожидаемый результат: что именно должно получиться.

Риски — начать можно, но работа может уйти не туда:
- key=success_criteria — Критерии успеха: Нет измеримых критериев: команда не поймёт, когда задача решена, а бизнес — принимать ли результат. Что добавить: Опишите критерии успеха: как поймёте, что решение сработало.
- key=constraints — Ограничения: Не указаны сроки, технологии и доступы: команда может выбрать стек или срок, которые бизнесу не подойдут. Что добавить: Укажите ограничения: сроки, технологии или доступы.
- key=business_link — Связь с бизнесом: Нет контакта или формата связи: вопросы команды останутся без ответа. Что добавить: Укажите контакт (почта или телефон), формат консультаций и порядок обратной связи.
```

**Системный промпт** (`app/trial.py`, константа `TRIAL_SYSTEM`, приводится дословно):

```
Ты — студенческая команда, которая получила карточку бизнес-задачи и пробует взять её в работу.
Правила:
- Опирайся ТОЛЬКО на карточку. Не добавляй фактов, чисел, названий, сроков и контактов, которых в ней нет.
- Составь план первой недели из 3–5 коротких шагов, по одному предложению. Где уместно, цитируй карточку в «кавычках».
- Если в списке есть блокеры, последний шаг плана — «Стоп: …» с blocked=true: дальше планировать нельзя. Если блокеров нет, у всех шагов blocked=false.
- Для каждого блокера и риска из списка напиши одной фразой, почему без этих сведений нельзя начать или что пойдёт не так, ссылаясь на то, чего именно нет в карточке. Ключи (key) бери из списка, новых не добавляй.
- Не оценивай бизнес и не предлагай готовых значений для пустых полей.
- Пиши только на русском языке.
```

**Выход модели** — JSON по схеме `TrialLLMResponse`: `steps` (3–5 шагов, у каждого `text` и `blocked`)
и `blockers` (`key` из списка выше и `reason`):

```json
{"steps": [
   {"text": "Разобрать, почему «около трети первокурсников не находят наставника»", "blocked": false},
   {"text": "Описать сценарий куратора: «трёх подходящих наставников на каждого первокурсника»", "blocked": false},
   {"text": "Стоп: в карточке нет ни анкет наставников, ни списков групп", "blocked": true}],
 "blockers": [{"key": "data", "reason": "Нет ни выгрузки, ни примера анкеты — начать разбор не с чего"}]}
```

**Защита от выдуманных фактов.** Все числа в ответе модели должны быть в карточке или в профиле
команды (номера дней и шагов 1–7 фактами не считаются); ответ с посторонним числом отбрасывается
**целиком**, ключи блокеров вне списка игнорируются, план короче трёх или длиннее пяти шагов — отбраковка.
Во всех этих случаях, как и при сетевой ошибке или невалидном JSON, включается заглушка: тот же вердикт
и те же блокеры, план из цитат карточки. Причина отката видна в подвале страницы и в `/health` (`ai_fallback`).
Проверяется в [tests/test_trial.py](tests/test_trial.py).

**Где видно.** Кнопка «Проверить глазами команды» в редакторе и страница `/business/cards/{id}/trial`.
Знак «прошла испытание» в каталоге и на странице задачи показывается, только пока подтверждённая версия
карточки совпадает с испытанной: правка после испытания снимает знак, а страница испытания предупреждает,
что результат устарел.

### Границы ИИ, заданные кейсом

- ИИ не добавляет фактов, которых не сообщил пользователь.
- Всё, что собрал ИИ, редактируется и подтверждается человеком до публикации: балл засчитывается
  только после подтверждения.
- ИИ не выбирает команду за бизнес и не назначает исполнителей.
- Персональные и чувствительные признаки участников не используются и не запрашиваются.

## Установка и запуск

### Системные требования

- Docker с docker compose — основной путь; либо Python 3.12+ — запасной. Проверено на Python 3.12 в образе и на Python 3.14 в локальном окружении
- Ключ OpenAI API — необязателен: без него приложение работает в режиме локальной заглушки ИИ, и основной сценарий проходит целиком

### Переменные окружения

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `LLM_PROVIDER` | нет, по умолчанию `openai` | `openai` или `nvidia` |
| `OPENAI_API_KEY` | нет | Ключ OpenAI. Пусто — режим заглушки |
| `OPENAI_BASE_URL`, `OPENAI_MODEL` | нет | Эндпоинт и модель, по умолчанию `gpt-4.1-mini` |
| `NVIDIA_API_KEY`, `NVIDIA_BASE_URL`, `NVIDIA_MODEL` | нет | Резервный провайдер |
| `APP_HOST`, `APP_PORT` | нет | По умолчанию `0.0.0.0:8000` |
| `DATA_PATH`, `SEED_PATH` | нет | Файл состояния и исходные данные |

Пример заполнения — в `.env.example`. Реальные ключи в репозитории отсутствуют.

### Основной путь: Docker

```bash
cp .env.example .env      # при желании вписать OPENAI_API_KEY
make run                  # = docker compose up --build
```

После запуска открыть <http://localhost:8000>.

Проверка состояния — `curl localhost:8000/health`:

```json
{
  "status": "ok",
  "ai_mode": "stub",
  "ai_fallback": null,
  "cards_total": 5, "cards_published": 5,
  "teams": 5, "proposals": 5, "drafts": 5,
  "store": "data/store.json",
  "version": "dev"
}
```

`ai_mode` — какой провайдер в работе: `openai`, `nvidia` или `stub` (без ключа). `ai_fallback` не пуст,
если ключ есть, но конкретный вызов модели не прошёл и сработала заглушка — режим виден честно,
а не выглядит так, будто модель отработала штатно.

Сброс данных к исходным: `make reset` (удаляет `data/store.json`, при следующем старте он создаётся из `data/seed.json`).

### Запасной путь: без Docker

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
python -m app
```

## Тестовые сценарии

Четыре сценария: первый — обязательная демонстрация из раздела 11 кейса, остальные закрывают
требования, которые в демонстрацию не попадают. Каждый проверен руками и покрыт автотестом.

### Сценарий 1 — обязательная демонстрация: слабый черновик → рост рейтинга → публикация → отклик → решение

Полный прогон с готовыми текстами и ожидаемыми баллами — [data/demo-scenario.md](data/demo-scenario.md).
Коротко: ввести черновик «Хотим чат-бота для студентов, чтобы отвечал на вопросы», ответить только
на первый из шести уточняющих вопросов — про данные и материалы, — получить карточку с рейтингом
**30 («Черновик»)**, дописать в редакторе оставшиеся поля и увидеть **100 («Приоритетная»)**,
подтвердить и опубликовать, найти задачу первой в каталоге, отправить отклик от студенческой команды
и вручную принять его. Числа сверены прогоном по коду, а не обещаны.

Автоматически: `make gate` — [tests/test_e2e.py](tests/test_e2e.py) проходит все девять переходов
за один запуск и проверяет в хранилище, что балл записывается только после подтверждения человеком.

### Сценарий 2 — правка опубликованной задачи и пересчёт

Открыть любую задачу из каталога → «Редактировать карточку» → изменить или дописать поле → «Сохранить».
Ожидаемо: предварительный балл пересчитан и показан рядом с подтверждённым, подтверждённый и позиция
в каталоге **не изменились**. Затем «Подтверждаю» → балл, уровень и позиция обновились.
Так выполняется требование «рейтинг пересчитывается после каждого подтверждённого дополнения».

### Сценарий 3 — несколько откликов и ручной выбор бизнеса

На странице задачи отправить два отклика от разных команд → у бизнеса принять первый.
Ожидаемо: первый «выбрана», второй по-прежнему «на рассмотрении» — решение по одному отклику
не трогает остальные. Принять второй → оба «выбрана». Третий отклик отклонить → первые два не изменились.
Повторное решение по уже решённому отклику не перезаписывается, выводится сообщение.

Автоматически: [tests/test_web_catalog.py](tests/test_web_catalog.py).

### Сценарий 4 — некорректный ввод

| Ввод | Ожидаемо |
| --- | --- |
| Пустой или пробельный черновик | сообщение на той же странице, черновик не создан |
| Отклик без идеи или плана | сообщение, введённое сохранено, отклик не создан |
| Отклик с неизвестной командой | сообщение |
| Ссылка на прототип не `http(s)://` | сообщение, отклик не создан |
| Значения фильтров каталога не из справочников | фильтр игнорируется, каталог полный, код 200 |
| Несуществующий id задачи или отклика | 404 |

Запасные примеры черновиков разной полноты — [data/examples.md](data/examples.md).

Если приложение уже запускали раньше, состояние лежит в `data/store.json` и сид повторно не читается.
Чтобы пройти сценарии с чистыми исходными данными кейса — `make reset` перед запуском.

### Сценарий 5 — испытание задачи виртуальной командой

Открыть редактор слабой карточки (например, сразу после ответов на вопросы) → «Проверить глазами
команды» → выбрать команду → отправить. Ожидаемо: «Не выдержала», план первой недели с шагом «Стоп»,
блокеры с ценой (за данные +20), следующий шаг с целевым баллом и уровнем. Заполнить названное поле,
сохранить → на странице испытания предупреждение «результат устарел» → повторить: блокер исчез.
Для карточки сида «Рекомендации курсов для студентов колледжа» (100 баллов): «Выдержала», блокеров нет,
в каталоге у задачи знак «прошла испытание». Баллы карточки от испытания не меняются.

Автоматически: [tests/test_trial.py](tests/test_trial.py).

## Ограничения

Честный список того, чего в проекте нет и почему. Там, где это наше решение, а не требование кейса,
указано основание.

### Сознательно не делали — кейс прямо разрешает

- **Шаг 8 сценария «Результат»** — баллы команде за фактический прогресс. Раздел 7 кейса: «полный
  проектный трекер — для демонстрации достаточно отклика и решения бизнеса по нему». Сквозной
  сценарий закрыт шагами 1–7.
- **Регистрация, восстановление пароля, ролевая модель.** Роль «бизнес» или «команда» — это раздел
  на странице, а не учётная запись. Раздел 7 кейса.
- **Чат, уведомления, календарь, файловое хранилище.** Раздел 7 кейса.
- **Своя ML-модель и векторная база.** Раздел 7 кейса; используется внешний API либо локальная
  детерминированная заглушка.
- **Мобильная адаптация.** Раздел 7 кейса. Вёрстка переживает узкий экран, но специально под телефон
  не проектировалась.

### Ограничения реализации

- **Без ключа API работает локальная заглушка.** Вопросы подбираются детерминированно по пробелам
  рейтинга, карточка собирается из ответов без переформулировки. Сквозной сценарий проходит целиком,
  но формулировки вопросов с реальной моделью богаче. Режим виден в подвале страницы и в `/health`.
- **Рейтинг пересчитывается после сохранения**, а не вживую в браузере по мере ввода. Требование
  кейса «пересчёт после редактирования» выполнено; живой пересчёт — вопрос удобства, не функции.
- **JSON-хранилище, один процесс.** Объём данных кейса — 5×4 сущности, файл проще и прозрачнее базы.
  Для нескольких одновременных пользователей понадобится СУБД: запись сериализована блокировкой
  внутри процесса, но несколько процессов один файл безопасно не поделят.
- **Состояние переживает перезапуск** в `data/store.json`, и сид повторно не читается. Чтобы вернуть
  исходные данные кейса — `make reset`.
- **NVIDIA как резервный провайдер** описан и реализован через ту же обёртку, но в соревновательное
  окно не проверялся. Критический путь — только OpenAI.
- **Каталог без пагинации и поиска.** При 5–50 задачах не нужны; сортировка и два фильтра есть.
