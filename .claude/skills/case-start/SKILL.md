# Запуск работы над кейсом

Соревновательное окно **13:00–18:00**, ровно 5 часов. Всё ниже привязано к этим часам.

Общий контекст, правила хакатона и запреты — в `CLAUDE.md`. Здесь только процедура дня.

Две мысли, на которых держится весь скилл.

**Тикет — это промпт для агента.** Каждый из троих работает через своего AI-агента и вставляет ему текст тикета. Другого контекста у агента нет. Слабый тикет = агент уходит не туда, расширяет объём, ломает чужие файлы. От качества тикетов зависит, соберётся проект или нет — поэтому на них не экономить.

**Структура работы выводится из кейса, а не берётся из шаблона.** Слои, лейны, лейблы, распределение между людьми — всё это определяется в фазе 0, когда кейс прочитан. Ниже есть типовые наборы, но они подсказка, а не предписание: подходят — берём, не подходят — делаем под кейс.

## Как работаем с git

Ветку заводит тот, кто делает задачу — под тикет или под фазу, как ему удобнее. Закончил — мержит в main. Появился конфликт — решает его.

```bash
git checkout main && git pull
git checkout -b HACKAI-N
# работа, сколько угодно коммитов
git checkout main && git pull
git merge HACKAI-N
git push
```

Короткую задачу можно сделать и прямо в main — `git pull`, поработал, `git add` своих файлов, `git commit`, `git pull && git push`.

Два момента, которые стоит держать в голове:

- **Готовое уезжает в main сразу**, а не копится к стыку фаз. Иначе интеграция откладывается на конец, а на пятичасовом хакатоне это дорого
- **Раздел «Файлы» в тикете** нужен, чтобы двое не правили один файл. Заметил проблему в чужом лейне — скажи владельцу, а не правь сам

**Перед каждой новой задачей — `git pull`, всегда, без исключений.** Это первое действие, ещё до чтения тикета и файлов. Пока ты делал предыдущую задачу, двое других что-то слили в main: новые функции, поправленные сигнатуры, обновлённый бриф. Начать без `pull` — значит работать на слепке получасовой давности и узнать об этом при слиянии.

## Как нарезать работу на троих

Готового списка лейнов нет. Слои у каждого кейса свои, и заранее их не угадать. Есть метод нарезки, который применяется в фазе 0, когда кейс уже прочитан.

### Единственное жёсткое требование

**Три потока работы, каждый в своих файлах.** Это не про роли и не про специализацию — это про то, что три человека одновременно правят один репозиторий. Всё остальное подбирается под кейс.

### Метод

**1. Выписать слои, которые в этом решении реально есть.** Не из шаблона, а из брифа. Слоем может оказаться что угодно:

логика и агентный цикл · подготовка и разбор данных · поиск и индексация · интеграции с внешними источниками · интерфейс или CLI · хранилище и состояние · правила и валидация · оценка качества результата · инфраструктура и сдача

У одного кейса слоёв будет четыре, у другого семь. У кейса без интерфейса слоя «интерфейс» просто нет, зато может быть «разбор документов» и «извлечение полей» как два отдельных.

**2. Один слой есть всегда — сдача.** README, воспроизводимость, смоук-тесты, демо-данные, подача решения. Он не зависит от кейса и стоит **40 баллов из 100**. Его нельзя оставлять на остаток и нельзя размазывать на всех — у него должен быть конкретный владелец.

**3. Сгруппировать остальные слои в два потока** по трём правилам, в порядке важности:

- **Минимум пересечения по файлам** — это главное, всё остальное вторично
- **Примерно равный объём** — чтобы закончили в одно время
- **Минимум блокировок** — если слой A нужен слою B, лучше их в один поток, чем в разные

**4. Назвать потоки тем, чем они в этом кейсе являются.** Не «ядро» и «поверхность» по привычке, а по сути: «разбор и извлечение», «проверка и оценка», «диалог и интерфейс». Понятное имя экономит объяснения весь день.

**5. Создать лейблы под эти имена** (см. следующий раздел).

**6. Раздать людям.** Сильные стороны — подсказка при прочих равных, а не закон. Дарья ближе к логике и бэкенду, Анель к интерфейсу, капитан хорошо закрывает дыры. Но если кейс требует иначе — распределяем иначе, это нормально: все трое работают через AI-агента, и незнакомая область влияет на скорость, а не на возможность.

Два соображения при раздаче:

- **Сдача — капитану**, если нет веских причин иначе. Работа прерываемая, а капитана весь день дёргают орг и решения по резке. Поток с глубоким контекстом от постоянных прерываний ломается, сдача — нет
- **Самый рискованный слой — тому, кто в нём сильнее.** Не из вежливости: если он не взлетит, переделывать будет некогда

**7. Между потоками зафиксировать контракт** — точные сигнатуры и форматы данных на стыке, дословно в `BRIEF.md`. Сколько бы потоков ни было, стык между любыми двумя описывается до начала работы. Без этого на интеграции ничего не сойдётся.

**8. Записать нарезку** в `BRIEF.md` и `PROGRESS.md`: кто на каком потоке, какие файлы чьи. Чтобы новая сессия не гадала.

### Что делать, если работа не делится на три

Бывает, что кейс узкий и третьему потоку взяться неоткуда.

| Ситуация | Что делать |
| --- | --- |
| Слоёв мало, объём маленький | Делим самый большой слой надвое по модулям, с контрактом между половинами |
| Один слой огромный, остальные крошечные | Двое на большом (разные модули), третий — сдача плюс всё мелкое |
| Слой не делится в принципе | Один делает, двое на сдаче и демо: тесты, данные, README, деплой, репетиция показа |

Простой третьего человека — худший вариант из всех. Лучше пусть делает демо-данные и README, чем ждёт.

### Лейблы

Делятся на две категории: **постоянные** — созданы заранее, не зависят от кейса; **под кейс** — создаются в фазе 0 после нарезки потоков.

**Постоянные:**

| Группа | Лейблы | Смысл |
| --- | --- | --- |
| Фаза | `фаза-0` `фаза-1` `фаза-2` `фаза-3` `фаза-4` | Наше расписание, от кейса не зависит |
| Приоритет | `мастхэв` `потом` | Из регламента: обязательное против отложенного |
| Свойства | `демо-путь` | Часть пути, который пройдёт жюри. Ломать нельзя, резать в последнюю очередь |
| | `блокер` | Кто-то прямо сейчас ждёт этого. Берётся вне очереди |
| | `быстрая` | До 15 минут. Чем заполнить окно, когда ждёшь чужого |
| | `свободная-очередь` | Никого не блокирует, берёт любой освободившийся |
| | `черновик` | Написан до понимания кейса, уточнить на стыке фаз |

**Под кейс — лейны.** Создаются в фазе 0 по результатам нарезки, именуются по сути потока: `разбор-документов`, `проверка-работ`, `диалог`, `сдача` — что угодно, лишь бы понятно с первого взгляда.

Три лейбла уже заведены как часто встречающийся набор: `ядро` · `поверхность` · `обвязка`. **Если они подходят кейсу — использовать их, если нет — создать свои и эти не трогать.** Неиспользованный лейбл никому не мешает.

**На одном тикете:** ровно одна фаза, ровно один лейн, `мастхэв` или `потом`. Свойства — сколько нужно, обычно ноль или одно.

Почему именно эти свойства:

- `демо-путь` отвечает на вопрос «что резать» на стыке фаз. Всё, что не на демо-пути, режется первым. Без этого лейбла на четвёртом часу начинается спор
- `блокер` отвечает на вопрос «что взять следующим» без единого сообщения в чат. Дублирует связи Linear, но виден прямо в списке, а связи надо открывать
- `быстрая` закрывает дыру в правиле про простой: освободился на 10 минут перед стыком — есть что взять

**Статусы:**

| Статус | Значение |
| --- | --- |
| `Backlog` | Черновики будущих фаз. Не брать |
| `Todo` | Готов к взятию: текущая фаза или свободная очередь |
| `In Progress` | Взят. Один человек — один тикет в этом статусе |
| `Done` | DoD пройден, мини-тест зелёный, **запушено в main** |
| `Canceled` | Ушло в «потом». Ставить лейбл `потом`, в комментарии — когда и почему |

**Связи:** блокировки проставлять через relations Linear (blocks / blocked by) и дублировать в описании тикета в разделе «Связи».

## Шаг 1. Получить вместе с кейсом

Если чего-то нет — спросить сразу, до начала работы:

- **Текст кейса дословно**, не пересказ. Формулировки обязательных условий имеют значение
- **Методику оценки по этому кейсу**, если организатор её выдал (общие критерии уже есть в `HACKALEM-CONTEXT.md`, их запрашивать не нужно)
- **Точное время закрытия репозитория**
- Доп. инструкции с площадки

## Шаг 2. Первые 10 минут — работать не спрашивая

Две вещи одновременно. Никто никого не ждёт.

**Развернуть каркас:**

1. Скопировать шаблоны из `prep/templates/` в корень, подставив выбранный стек
2. Поставить скелет: точка входа, конфиг, `.env.example`, `requirements.txt`
3. Заполнить шапку `PROGRESS.md`: время старта, обратный отсчёт, кейс
4. **Первый коммит.** Час 1 обязан иметь подтверждение прогресса

**Разобрать кейс и написать `BRIEF.md`** в корне:

| Раздел | Что внутри |
| --- | --- |
| Проблема | Что решаем и для кого |
| Мастхэв из кейса | **Цитатами** из текста, не пересказом |
| Мастхэв из критериев | README, воспроизводимость, рабочий сквозной сценарий, проверка |
| Что на выходе | Одно проверяемое предложение: вход → результат |
| Слои решения | Из чего это реально состоит в данном кейсе, с оценкой объёма каждого |
| Нарезка потоков | Три потока, кто на каком, какие файлы чьи — по методу из «Как нарезать работу на троих» |
| Контракт | Формат данных на стыках лейнов — сигнатуры дословно |
| Стек | Выбранный, с одной строкой обоснования |
| Провайдеры | Что через OpenAI, что через NVIDIA (см. шаг 4) |
| Потом | Всё, что не влезает. Не выброшено — отложено |
| Время | Оценка по пунктам. **Сумма мастхэва ≤ 4 часов** |

Бриф пишется **за 10 минут и на одну страницу**. Если превращается в документ — съедает то время, ради которого создаётся.

Правила брифа:

- Мастхэв бывает двух видов, и второй забывают: требования кейса и требования оценки. Оба обязательны
- «Что на выходе» — проверяемое предложение, которое дословно уедет в README в «как проверить решение». Не «система для X», а «пользователь делает A и получает B»
- **Слои выписываются до нарезки потоков.** Пока не видно, из чего состоит решение и сколько в каждом слое работы, делить между людьми нечего
- **Контракт фиксируется здесь и копируется в тикеты дословно.** Это единственное, что связывает лейны. Если сигнатуры в двух тикетах разойдутся — на стыке ничего не соберётся
- Поверхность делаем ровно такой, какой требует кейс. Полноценный UI только если кейс требует или без него не показать сценарий. Интерфейс — классическая яма на пять часов
- Не влезает в 4 часа — режем **сейчас**, не на четвёртом часу

## Шаг 3. Единственная точка ожидания

Капитан читает бриф и говорит «ок» или правит. Две-три минуты. Подтверждает в том числе **нарезку потоков** — кто на чём.

Доменная логика стартует только после этого. Всё остальное к этому моменту уже крутится.

**Если обязательные требования не помещаются в 5 часов** — сказать вслух: режем до самого узкого сценария, который работает целиком? Наполовину сделанное не набирает баллов: оценивается только фактически работающая функциональность. Решение принимает капитан.

## Шаг 4. Провайдеры LLM

Решается один раз в брифе, не в каждом тикете.

**Правило: один провайдер в критическом пути.** Два провайдера на основном сценарии — это два способа упасть на демо. Основной — **OpenAI**: лучшая поддержка структурированного вывода и вызова инструментов, команда его знает, у каждого свой ключ.

**NVIDIA — по назначению, а не «на всякий случай».** Подключать только если кейсу нужно:

| Задача | Провайдер | Почему |
| --- | --- | --- |
| Рассуждение, агентный цикл, генерация ответа | OpenAI | Качество, structured output, tool calling |
| Эмбеддинги и реранк для RAG | NVIDIA | Есть специализированные модели, OpenAI-совместимый эндпоинт |
| Массовые дешёвые вызовы: классификация, извлечение полей | NVIDIA (открытая модель) | Кредит расходуется на порядок медленнее |
| Речь (ASR/TTS), OCR | NVIDIA | У OpenAI это дороже или отсутствует |
| Резерв, если OpenAI лёг | NVIDIA | Переключение одной переменной в `.env` |

**Одна обёртка на всех.** `app/llm.py` читает из env `LLM_PROVIDER`, `<PROVIDER>_API_KEY`, `<PROVIDER>_BASE_URL`, `<PROVIDER>_MODEL`. Оба провайдера ходят через один `openai` SDK: NVIDIA Build совместим с OpenAI API по адресу `https://integrate.api.nvidia.com/v1`. Внутри обёртки — таймауты, ретраи, JSON-режим. **Никто не зовёт SDK напрямую**, только через обёртку. Это делает провайдер настройкой, а не переписыванием.

**В тикетах** провайдер не указывается. Указывается «через `app/llm.py`». Исключения: тикет самой обёртки и тикеты, где нужна конкретная возможность (эмбеддинги → NVIDIA, с указанием модели).

**Имена моделей NVIDIA** брать с `build.nvidia.com/models` в день старта — каталог меняется. Ориентиры: `meta/llama-3.1-70b-instruct`, `nvidia/llama-3.1-nemotron-70b-instruct`, для эмбеддингов `nvidia/nv-embedqa-e5-v5`. Проверить перед использованием.

**Ключи** — только в `.env`, никогда в коде и коммитах. Перед каждым пушем: `git grep -nE "sk-[A-Za-z0-9]|nvapi-"` должен молчать.

| Поле | Правило |
| --- | --- |
| Заголовок | Глагол + объект. «Реализовать обёртку над LLM», не «LLM» |
| Исполнитель | Всегда назначен. Тикет без исполнителя не существует |
| Лейблы | Ровно одна фаза + ровно один лейн + `мастхэв` или `потом`. Плюс `свободная-очередь` или `черновик` при необходимости |
| Статус | По таблице выше |
| Оценка | В минутах, в описании. 30–60 мин на тикет. Больше 60 — дробить |
| Связи | Blocks / blocked by через relations |

### Почему каждый раздел обязателен

- **Контекст** — агент стартует с нуля. Без ссылки на бриф он будет угадывать, что за проект
- **Что уже есть** — без этого агент перепишет то, что сосед уже сделал, или проигнорирует готовую функцию и напишет свою
- **Контракт** — единственный механизм интеграции между лейнами. Расхождение сигнатур обнаруживается на стыке, когда чинить дорого
- **Готово когда** — «работает» не проверяется. «Функция возвращает объект с полями X, Y на входе Z» — проверяется
- **Мини-тест** — команда, которую запускает и агент перед пушем, и сосед при проверке, и эксперт при оценке. Одна и та же
- **Файлы / Не трогать** — чтобы двое не правили один файл. Ветка от этого не спасает: конфликт всё равно всплывёт при слиянии. Три агента без этого раздела гарантированно столкнутся
- **Не делать** — агент увидит соседнюю проблему и полезет чинить. Граница объёма удерживает его в лейне
- **Связи** — чтобы освободившийся видел, что можно брать, а что заблокировано, не спрашивая
- **Сдача** — единый ритуал из четырёх команд. Без `git pull` перед `push` — отказ. Без `make check` — сломанный main для всех

### Пример готового тикета

````markdown
```
````

## Следы работы: что агент пишет и где

Три агента работают параллельно в одном репозитории и не видят друг друга. Код в main показывает, **что** изменилось, но не показывает, что теперь можно звать, где грабли и чем реальность отличается от плана. Без этого следующий агент либо переспрашивает человека, либо угадывает.

### Где что пишется

| Куда | Кто пишет | Что |
| --- | --- | --- |
| **Комментарий в тикете Linear** | Агент, делавший задачу | Отчёт о готовности или о застревании |
| **`PROGRESS.md`** | **Только Claude капитана** | Сводное состояние проекта |
| **Сообщение коммита** | Агент | `[HACKAI-N] что сделано` |
| **Докстринги** | Агент | На функциях, которые зовут из чужих потоков |

**`PROGRESS.md` пишет один человек.** Это единственный файл, интересный всем сразу, — если в него начнут писать трое, он превратится в постоянный конфликт при слиянии. Агенты Даши и Анель в него **не пишут никогда**, только читают.

### Отчёт о готовности — обязателен перед переводом в Done

Закончил тикет → комментарий в Linear → статус Done → код в main. Без комментария тикет не считается закрытым.

```markdown
## Сделано
<что фактически работает, 1–2 предложения>

## Что теперь можно звать
<точные сигнатуры, эндпоинты, файлы, доступные другим потокам — с путями>
<если ничего наружу не торчит — «ничего, внутреннее»>

## Отклонения от тикета
<чем реальность отличается от того, что было написано>
<если менялся КОНТРАКТ — написать это первой строкой и капслоком>
<если отклонений нет — «нет»>

## Файлы
Создано: <пути>
Изменено: <пути>

## Проверка
<команда> → <что увидишь>

## Осталось
<что не доделал и почему; что уходит в «потом»>
<если всё — «ничего»>

Коммит: <короткий хеш>
```

Самое ценное здесь — **«что теперь можно звать»** и **«отклонения»**. Первое избавляет соседа от чтения чужого кода, второе ловит расхождение контракта в момент возникновения, а не на интеграции.

**Изменение контракта — отдельный случай.** Если пришлось отойти от того, что записано в `BRIEF.md`, агент обязан: написать это в комментарии первой строкой, сказать человеку вслух, и человек говорит капитану. Молча разошедшийся контракт — самая дорогая ошибка дня: она всплывает на стыке фаз, когда переделывать уже некогда.

### Сигнал о застревании — если больше 15 минут

```markdown
## Застрял
<в чём проблема>

## Что пробовал
<кратко, чтобы следующий не повторял>

## Что нужно
<решение капитана / чужой тикет / доступ / уточнение кейса>

Потрачено: <N> мин
```

Плюс сказать человеку, чтобы он сказал вслух. Молчаливое отставание обнаруживается на стыке фаз, когда перестраиваться дорого.

### Ритуал взятия задачи

Агент, берущий тикет, **до первой строки кода**:

1. **`git pull` — первым действием, всегда.** За время предыдущей задачи в main уехала чужая работа: новые функции, изменённые контракты, обновлённый `BRIEF.md`. Читать файлы до `pull` бессмысленно — прочитаешь устаревшее
2. Читает `CLAUDE.md`, `BRIEF.md`, `PROGRESS.md` — уже в свежем виде
3. Читает свой тикет целиком, включая «Файлы» и «Не делать»
4. **Читает комментарии в тикетах, которые его блокировали** — там написано, что появилось и с какими отклонениями
5. Проверяет, что обещанное блокирующими тикетами действительно есть в коде

Первый пункт не формальность. Работа без `pull` — это работа на слепке получасовой давности: дублируешь то, что сосед уже сделал, зовёшь функцию по старой сигнатуре, получаешь конфликт при слиянии там, где его могло не быть.

Пятый пункт не паранойя: комментарий мог быть написан до того, как код уехал в main.

### Докстринги на публичных границах

Комментарии в коде по умолчанию не пишем. Исключение — **функции и классы, которые зовут из чужих потоков**: у них должен быть короткий докстринг с тем, что принимает и что возвращает. Это то, что сосед прочитает вместо того, чтобы разбирать реализацию.

Внутри своего потока докстринги не нужны.

### Что делает Claude капитана

Раз в 20–30 минут и перед каждым стыком фаз: читает новые комментарии в Linear, сводит в `PROGRESS.md`, ловит расхождения контракта и то, что кто-то тихо застрял.

## Шаг 6. Стартовый набор тикетов

Это **не готовый список задач**, а перечень того, что в проекте такого рода нужно почти всегда. В день старта: сопоставить с брифом, выкинуть лишнее, добавить недостающее по кейсу, разложить по нарезанным потокам, заполнить `<…>`, создать.

Колонка «слой» — про характер работы, не про имя лейна. Лейны именуются по кейсу, и тикет получает тот лейбл, который создан в фазе 0.

Фазы 0–1 создаются детально по шаблону из шага 5. Фазы 2–4 — заголовками, с лейблом `черновик` и статусом Backlog.

| Фаза | Время | Цель |

## Шаг 8. Против простоя — три правила

**1. Слияние непрерывное.** Лейны разделены по файлам, каждый готовый тикет уходит в main сразу, независимо от того, шёл он напрямую или через ветку. Состояния «закончил и жду слияния» не существует. Стык фаз — это проверка и перепланирование, а не момент слияния.

**2. Закончил раньше — три шага строго по порядку.**

Фаза не является стеной для личной работы. Это точка сверки для команды. Закончил своё — работаешь дальше, а не ждёшь.

0. **Если где-то висит `блокер`** — берётся вне всякой очереди, кто-то из своих уже ждёт
1. **Свободная очередь.** Там мастхэв по критериям — демо-данные, смоук-тесты, README, проверка сборки. Писать новую функциональность, когда README не начат, — плохой размен. До стыка осталось десять минут — брать с лейблом `быстрая`
2. **Следующий тикет в своём лейне**, даже если он формально из следующей фазы. Но только **не заблокированный чужой незаконченной работой**. Для этого у тикетов проставлены блокировки — чтобы не гадать, а видеть

   Пример: поток ввода-вывода закончил фазу 1. В фазе 2 у него два тикета: «подключить реальные данные» зависит от чужой логики — брать нельзя; «обработка неверного ввода» только в своих файлах — берётся и делается
3. **Помочь отстающему**, но только отделяемым куском, **в своих файлах или в новом файле**. Чужие файлы не трогать — ветка от конфликта не спасёт

**Не убегать больше чем на одну фазу вперёд.** Работа на две фазы вперёд строится на предположениях, которые изменятся, и её придётся переделывать. В такой момент — свободная очередь или помощь другому.

Сверка происходит **по часам, а не по готовности**. Кто-то ушёл вперёд — на стыке это видно, и расписание при необходимости сжимается.

**3. Отстаёшь больше 15 минут — говоришь сразу**, не дожидаясь стыка. Тогда либо дробим тикет и часть уходит свободному, либо переносим остаток. Молчаливое отставание обнаруживается на стыке, когда перестраиваться уже дорого.

## Шаг 9. Стык фаз — 5 минут, порядок фиксированный

1. Всё запушено, **main зелёный**: сборка и смоук проходят
2. Сверка с брифом: какие мастхэвы закрыты, какие остались
3. **Время: успеваем или режем.** Что уходит в «потом» — решает капитан
4. Тикеты следующей фазы: снять `черновик`, уточнить по факту, перевести из Backlog в Todo, лишнее — в Canceled с лейблом `потом`
5. Состояние в `PROGRESS.md`, коммит

Пункты 1–3 Claude готовит заранее, к моменту сбора сводка уже на руках.

**Главное на стыке — не «что добавить», а «что режем».** Если сверка сводится к добавлению задач, объём растёт монотонно и к пятому часу не доделано ничего. Добавлять стоит только пропущенное **обязательное требование кейса**. Всё «хорошо бы» — в «потом», без обсуждения.

Порядок резки задаёт лейбл `демо-путь`: сначала уходит всё, что вне демо-пути, и только если этого мало — трогаем сам демо-путь. Спорить не о чем, расстановка сделана заранее.

Перенос в «потом» это не потеря: он же станет разделом ограничений в README и ответом на критерий «потенциал развития» на Demo Day.

## Шаг 10. Жёсткие отсечки — по часам, независимо от готовности

| Время | Что происходит |
| --- | --- |
| **к 15:00** | Решение подано черновиком через «Сдать решение». Дальше обновляется |
| **17:00** | **Заморозка функциональности.** Что не работает — в «потом». Дальше только README и проверка |
| **17:30** | Сборка с нуля без кеша, прогон сценария |
| **17:45** | Финальные коммиты |

Подача на втором часу убирает целый класс катастроф: «сделали, но забыли нажать кнопку». Решение обновляется до дедлайна, так что подать рано ничего не стоит.

Без отсечки на 17:00 команда кодит до последней минуты, а README и проверка запуска не случаются. Это 40 баллов, потерянных из-за отсутствия будильника.
